Compute and Camera Options

The project runs mostly on hardware we already have: one GPU workstation, and now a second PC, siix-pc, with a 20 GB workstation GPU. Two items still need spending: GPU time for the one large training run, and power for the depth camera. This page compares the options for each, with time and cost.

1. Training compute

The problem

One workstation (16 GB GPU, 20 cores) currently does everything: simulation, data generation, evaluation and training. Two things slow it down:

  • The new model is bigger. SmolVLA is several times larger than the policy I trained before. On 16 GB it trains with small batches, so each run is roughly 2–3× slower than on an 80 GB data-centre GPU.
  • Everything waits in line. While the workstation trains, it can't generate data or test the model. Each round of "generate, train, test, fix" runs one step at a time.

siix-pc

A second PC, siix-pc, is available: NVIDIA RTX 4000 Ada (20 GB), Intel Core Ultra 7 265K (20 cores), 64 GB RAM. It fixes the second problem but not the first:

  • It removes the waiting. One machine trains while the other generates data and tests the model. With both generating, data takes half as long.
  • It doesn't make a training run shorter. It's a low-power (130 W) card with about half the memory speed of the current workstation, so a run takes about as long as on the current workstation, or a bit longer. Its 20 GB allows somewhat larger batches.

So the two machines handle data generation, pilots, testing and the smaller fine-tunes for free. Renting a GPU now only makes sense for the one large main training run, where an A100 is 2–3× faster.

How the cost stays capped

  • Prepaid credit: $50 is loaded onto the RunPod account in advance, with no auto top-up. Spending can't go above it.
  • Pilot first: every training setup is tested on our own machines before the rented GPU is used.
  • Only the main run is rented: fine-tunes, pilots and testing stay on our two machines.
  • Auto-stop: the rented machine shuts itself down when a run ends, so idle time isn't billed.
  • Frequent checkpoints: a saved copy every 2,000 steps means a lost machine costs minutes, not hours.
  • Expected spend under option C is $30–35. The rest of the $50 is a buffer for a failed start. If the main run on our own machines turns out fast enough in the speed test, nothing is rented at all.

2. Depth camera power

The problem

The new task finds objects anywhere on the table using the depth camera on the robot's wrist (Orbbec Gemini 2). That camera is on a port supplying 900 mA, below its 1.5 A requirement. It already resets during use: the system log shows it dropping off the USB bus. I wrote software that restarts it automatically, which keeps the robot safe, but each reset interrupts a test. The depth stream, unused so far, draws more power and makes resets more likely.

If this isn't fixed, failures in object finding could come from power drops rather than from the method. That makes results hard to trust and costs testing time.

D. Separate power supply for the camera~$15–30Only if this camera model accepts external power; needs checking in Orbbec's documentation

Recommendation

  • Compute: use both our machines (option B), plus one rented A100 run for the main training (option C), capped by $50 prepaid credit. Expected spend $30–35. Saves about a week over our machines alone, and 2–3 weeks over the current setup.
  • Camera: try option B (free) first; if resets continue, buy a powered hub (~$40).
  • Total request: up to $90, expected $30–75.
